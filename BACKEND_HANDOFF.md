# GGYM Backend Handoff

## 1. Purpose

This document is the backend source of truth for rebuilding the frontend or moving the project to another workspace.

The backend is a multi-tenant gym SaaS platform. A Facility is a tenant. Data that belongs to a gym must always be scoped by the facility identity derived from the authenticated token.

Frontend must not invent permissions or send a facility id through query strings or custom headers. Use route parameters on supervisor-only platform endpoints, or use the facility-scoped token generated by the backend.

## 5. Authentication Flow

### 5.1 Supervisor

1. POST /api/auth/login/supervisor with email and password.
2. The response returns a temporary token:
   - First TOTP setup: QR URI plus tempToken.
   - Existing TOTP: tempToken for code verification.
3. POST /api/auth/verify-totp with tempToken and code.
4. The response returns data.token and data.mustChangePassword.
5. If mustChangePassword is true, call POST /api/auth/change-password.
6. Replace the old token with the new token returned by change-password.
7. Call GET /api/auth/me to hydrate the frontend session.

The must-change-password middleware allows only these protected operations while the flag is true:

- GET /api/auth/me
- POST /api/auth/change-password
- POST /api/auth/logout

All other protected endpoints return 403 until the new token is used.

### 5.2 Owner

POST /api/auth/login/owner returns a normal JWT and owner access state:

- contractSigned
- onboardingCompleted
- facilityStatus

The owner dashboard is gated by contract and onboarding rules already implemented in the backend.

### 5.3 Staff

POST /api/auth/login/staff supports:

- BranchManager
- Coach
- Receptionist

The result contains:

- token
- role
- facilityId
- branchId when the role is branch-specific

### 5.4 Session and logout

GET /api/auth/me returns the current session:

- userId
- email
- actorType
- facilityId
- branchId
- isImpersonating
- onBehalfOfRole
- mustChangePassword

POST /api/auth/logout requires authentication. Every issued JWT has a unique jti. Logout stores that jti in RevokedTokens, so the token is rejected server-side even before its normal expiry.

Normal JWT lifetime is 7 days. Impersonation JWT lifetime is 45 minutes.

## 6. Authentication Claims and Tenant Rules

Normal JWT claims include:

- nameidentifier
- email
- role
- actor_type
- must_change_password
- token_version
- facility_id when facility-scoped
- branch_id when branch-scoped
- jti

Impersonation JWT claims include:

- supervisor_id
- actor_type = SUPERVISOR
- role equal to the selected target role
- on_behalf_of_role
- facility_id
- optional branch_id
- is_impersonating = true
- jti

Never send facility_id in query strings or headers. TenantResolutionMiddleware rejects those attempts with HTTP 400.

The DbContext applies global tenant filters. A normal supervisor session is global. Facility-scoped sessions are limited to the facility in the token. Branch-scoped sessions are additionally limited to the branch in the token.

Important impersonation behavior: an impersonation token simulates a selected role and carries the supervisor identity underneath. It is not a login as a specific owner or employee. The frontend should use it primarily for facility/role preview and must always respect the selected role permissions.

## 7. Role Summary

### Supervisor primary session

Can:

- View and manage all facilities.
- Create, update, lock, unlock, and delete facilities.
- View facility details, branches, platform subscription, players, and player subscriptions.
- Manage owners.
- Create, list, activate, deactivate, and reset employee accounts.
- View platform dashboard counts.
- View detailed payment records and grouped reports.
- Create and activate add-on features.
- Read all support tickets, reply, and close tickets.
- Read all audit logs.
- Read and manage supervisor notifications.
- Impersonate Owner, BranchManager, Coach, or Receptionist.

Cannot impersonate:

- Supervisor
- System

Sold-license facilities cannot be impersonated and do not expose add-ons.

### Owner session

Can use facility-scoped owner workflows:

- GET /api/auth/me
- GET /api/owners/me
- POST /api/owners/onboarding
- GET /api/contracts/current
- POST /api/contracts/sign
- POST /api/branches
- GET /api/branches
- POST /api/players
- GET /api/players
- POST /api/support/tickets
- GET /api/support/tickets
- POST /api/support/tickets/{id}/messages
- POST /api/auth/change-password
- POST /api/auth/logout

### BranchManager, Coach, Receptionist

They receive facility and optional branch claims through staff login. Existing facility-scoped reads and writes must continue to enforce the role-specific business rules in their handlers. Do not expose supervisor-only screens to them.

## 9. Standard Errors

Successful responses use:

    { "success": true, "data": ... }

Errors use the exception middleware and include a status code/message structure. Main statuses:

- 400: invalid input or forbidden facility id transport.
- 401: missing, expired, malformed, or revoked token.
- 403: authenticated but role or workflow not allowed.
- 404: resource does not exist or is intentionally hidden, such as Sold facility add-ons.
- 409: duplicate or conflicting operation.
- 429: rate limit exceeded.

Frontend should handle 401 by clearing the current session and returning to login. Do not treat a 403 as a login failure.

## 10. Data Model

Main entities:

- Supervisor: the platform administrator and TOTP owner.
- Facility: gym tenant and license state.
- Owner: one or more facility owner records.
- Branch: facility branch.
- BranchManager, Coach, Receptionist: staff accounts.
- Player: facility player with optional subscription assignment.
- Subscription: player subscription record.
- PlatformSubscription: facility platform license record.
- PaymentRecord: internal payment ledger.
- AddOnFeature: platform add-on catalog item.
- FacilityAddOnSubscription: facility add-on activation.
- Contract and ContractApproval: versioned owner contract workflow.
- SupportTicket and SupportTicketMessage: internal support communication.
- AuditLogEntry and AuditLogArchive: audit history.
- Notification: per-actor in-app notification.
- RevokedToken: server-side JWT revocation record.

## 11. Security Rules

- Passwords are BCrypt hashes and must never be returned by an API.
- TOTP secrets are encrypted at rest.
- Supervisor token versions invalidate older supervisor tokens after password changes.
- Every JWT has a unique jti and logout revokes it.
- Idempotency-Key prevents duplicate payment records for unlock and add-on activation.
- Facility and branch ownership is checked before creating or moving players and staff.
- Supervisor-only queries use explicit role checks in application handlers.
- Do not trust a role sent in the request body without validating it.
- Do not trust facility ids from headers or query strings.
- Keep JWT, encryption, and database secrets outside source control in production.
- Persist ASP.NET Data Protection keys outside the container in production.
- Configure HTTPS and trusted reverse proxy headers before production deployment.

## 13. Known Limitations and Next Backend Decisions

- The payment layer records internal/offline payments only.
- There is no external email, WhatsApp, or push notification provider.
- Notifications currently cover support tickets, facility lock/unlock, and add-on activation.
- The supervisor impersonation token selects a role and facility but does not identify a real target employee.
- The player subscription model currently represents created assignment records; a separate reusable plan catalog may be needed later.
- EF reports warnings about required entities with global query filters for ContractApproval and SupportTicketMessage. The application starts and migrations apply, but these relationships should be made optional or given matching filters before a production hard-delete/soft-delete policy is finalized.
